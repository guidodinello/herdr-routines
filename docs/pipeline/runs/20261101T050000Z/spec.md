# spec v2 — issue 077: move `gated` jobs' `github_event` checks onto `trigger.event`

Run: 20261101T050000Z · Issue: `docs/process/issues/077-gated-github-event-checks-as-event-triggers.md` · Related: 014, 075, 076 (golden-test pattern), 070. v1→v2 changes are listed in [`## Changelog v1→v2`](#changelog-v1v2).

## Problem

Two mechanisms answer "did a matching event happen?":

1. **014's gated `github_event` check** — polled only when the job's cron fires (`tick._gated_cycle` → `_process_event_target`, tick.py:3388-3401). Own watermark (`last_seen_event_ids` in history extras, read back by `_last_seen_event_ids`), per-event attempt budget (`attempt_count_for_event` vs `max_attempts_per_target`, tick.py:1400), head-ref validation, fail-closed poll errors, `issues:opened` baseline adoption.
2. **075's `trigger.event`** — polled every tick (`_poll_event_trigger`, tick.py:3136). Fires the job via `dispatch_occurrence`; watermark written *before* dispatch (at-most-once); retries left to the job's `retry_on`/`fallback_model`; no per-event budget.

`config.py:1605-1608` rejects `trigger.event` on a gated job that has a `github_event` check, because both would write the same per-job watermark. The gated check is the special-casing 071's dispatch split exists to remove. Note: `checks` cannot mix kinds (config.py:1541-1544), so any gated job with a `github_event` check has that check as its *only* check — the migration target is always "the check *is* the gate" and is clean.

## Approach

1. **Golden test first (076's pattern).** Commit `test_gated_event_check_behaviour_unchanged_after_migration` on unmodified code; verify it passes before touching anything. It pins: poll → dedup against watermark → per-fire behavior (dispatch, over-cap deferral, `max_attempts_exceeded` skip with notification, head-ref skip vs retry, poll failure fail-closed, `issues:opened` first-poll baseline adoption) and the history-record shapes each step writes.
2. **Config sugar, not file migration (076's `kind: review` precedent).** A gated job whose checks are all `github_event` loads unchanged; `load_config` normalizes it — `job.trigger_event` is set from the check's shape (`query`/`repo`/`match`), and the cron-path checks no longer carry the predicate. No one-time migration of the Pi's file is needed (and the committed `deploy/jobs.d/babysit-prs.yaml` uses `pr_health`, untouched). A job that explicitly declares *both* `trigger.event` and a `github_event` check is a load error (it used to be implicitly rejected at config.py:1605 — now spell the conflict out); the blanket 075 rejection is removed.
3. **Single mechanism in the tick.** `_gated_cycle` loses its `github_event` branch; the moved job's event firing goes through `_poll_event_trigger`. The 014-specific logic that must survive the move lifts out of `_process_event_target` into the trigger path:
   - **Per-event attempt budget (retained — this is the issue's decisive question).** Before dispatching an event, the trigger path checks `attempt_count_for_event(history, job, event_id)` and records `skipped / max_attempts_exceeded` (same extras, same notification policy hook) when it is exhausted. Vanilla jobs that declare `trigger.event` directly keep 075's at-most-once semantics; only migrated gated jobs get the budget. Why: a gated job is an unattended fix workflow whose individual dispatch plausibly fails transiently (dirty worktree, bad head ref) — at-most-once would drop fixes silently, which is exactly the failure class 014's budget exists to prevent. A routine job firing on an event can afford at-most-once because its `retry_on`/`fallback_model` own retry policy.
   - **070's dirty-worktree rule retained.** The fired event still flows into the same pr-target fix path with the event's enriched context (PR number, head ref) so `worktree_reuse_not_clean` refusal and `_dirty_worktree_already_reported` behave as before.
   - Fail-closed poll errors, `issues:opened` baseline adoption, and the "event clears and comes back fires again" watermark rule carry over unchanged.
4. **AC2 — `test_single_event_watermark_per_job`:** for any job (declared or sugar-loaded) exactly one history path writes `last_seen_event_ids`; the config-level dual-writer conflict is gone because the dual writer is, not because a validation error masks it.
5. Docs/examples touch-ups where the two mechanisms are described (`deploy/jobs.example.yaml`, `ROADMAP.md` G-98 area, issue-014/075 references), plus removal of the stale "cannot be combined" validation text.

## Risks

- [blocking] **Record-shape drift breaks readers, not just readers-of-tests.** `_last_seen_event_ids` reads the latest terminal record carrying the key; `attempt_count_for_event` scans history; `status`/notifications key off `gate`/`reason`/`phase`. The crossed-out 014 path wrote `gate=passed/baseline/failed` with a `run_id`; the 075 path writes `trigger=event, phase=event_poll`, often without a run_id. The golden test pins the externally observable shapes; acceptance criterion 1 means the *after* code must write shapes the same consumers understand, so the lifted logic writes 014-shaped records from the trigger path rather than thinning them into 075's quieter shapes. — confidence: high (verified against the read sites: `_last_seen_event_ids`, `attempt_count_for_event`, `status`/notify hooks)
- [blocking] **First tick after upgrade.** Watermarks written by the old path must be read by the new one without refiring or dropping events (`issues:opened` baseline adoption re-arms only when no watermark exists — an existing watermark must prevent a spurious re-baseline). — confidence: high (property pinned by the golden test and the dedup/baseline tests)
- [non-blocking] **Timing change is accepted, stated.** The poll cadence moves from the job's cron to every tick: events fire sooner. Same events, same skips, same budget (AC1's terms) — but notification cadence for `notify_policy: on-finding`-style jobs rises. Accepted as the point of the unification; noted so it isn't mistaken for a bug. — confidence: high
- [blocking] `validate`'s tick-timeout budget (one poll with `check.timeout_ms` per tick per such job) must still hold for sugar-loaded jobs on every-tick cadence. — confidence: medium (budget arithmetic `_check_systemd_timeout` is pinned, but the every-tick × event-poll interaction has no live measurement)

## Acceptance criteria

1. [blocking] Golden test first (076's pattern): `test_gated_event_check_behaviour_unchanged_after_migration` is committed on the unmodified code and verified passing before any src change. It pins the full externally observable behaviour — poll → dedup against the watermark → dispatch, over-cap deferral, `max_attempts_exceeded` skip with its notification, head-ref skip vs retry, fail-closed poll errors, `issues:opened` first-poll baseline adoption (and an existing watermark preventing a spurious re-baseline), the "event clears and comes back fires again" watermark rule — plus the history-record shapes each step writes (`gate`/`reason`/`phase`/`run_id`, `last_seen_event_ids`, budget extras). After the migration the same test passes unmodified: same events fire, same skips, same per-event attempt budget (issue 077's AC1). — confidence: high — Test: test_gated_event_check_behaviour_unchanged_after_migration
2. [blocking] Only one watermark writer per job remains: for any job — one declaring `trigger.event` directly and one sugar-loaded from a gated `github_event` check — exactly one history path writes `last_seen_event_ids`. The dual-writer conflict is gone because the dual writer is gone, not because a validation error masks it (a test proves two loads/writers cannot coexist for the same job). — confidence: high — Test: test_single_event_watermark_per_job
3. [blocking] Config sugar, not file migration: a gated job whose only check is `github_event` loads unchanged; `load_config` normalizes it so `job.trigger_event` is set from the check's shape (`query`/`repo`/`match`) and the cron-path checks no longer carry the predicate. A job that explicitly declares *both* `trigger.event` and a `github_event` check is a load error (the old implicit rejection at config.py:1605–1608 is spelled out); the blanket 075 rejection of `trigger.event` on gated jobs is removed, and mixed-kind checks stay rejected per config.py:1541–1544. — confidence: high — Test: test_github_event_config_validation
4. [blocking] The per-event attempt budget survives the move for migrated gated jobs: before dispatching an event, the trigger path checks `attempt_count_for_event(history, job, event_id)` and, when exhausted, records `skipped / max_attempts_exceeded` with the same extras and the same notification policy hook. Migrated gated jobs keep 014's retry-on-failure; vanilla `trigger.event` jobs keep 075's at-most-once (the decided design question, with 070's rationale). — confidence: high — Test: test_github_event_budget_exceeded_skips_with_notify
5. [blocking] Fail-closed poll errors carry over: a poll that errors does not fire the event, writes the fail-closed history record the golden test pinned, and never consumes the event. — confidence: high — Test: test_github_event_api_failure_fails_closed
6. [blocking] Head-ref validation carries over: an invalid head ref is skipped without creating a worktree, and a head-ref check that cannot run is a retried failure (staying green as `test_head_ref_check_that_cannot_run_is_a_retried_failure`). — confidence: high — Test: test_invalid_head_ref_is_skipped_without_a_worktree
7. [blocking] Baseline adoption survives the move: a first poll with no watermark adopts open issues as the baseline rather than dispatching everything, a failed first poll does not count as baseline, and an empty first poll still counts as polled (all existing records-unchanged). — confidence: medium (adoption logic is data-driven and previously only exercised through the 014 path; the golden test exercises it through the trigger path) — Test: test_issues_opened_first_poll_adopts_open_issues_as_baseline
8. [blocking] 070's dirty-worktree rule survives: a fired event flows into the same pr-target fix path with the event's enriched context (PR number, head ref), so a `worktree_reuse_not_clean` refusal is recorded and does not consume an attempt. — confidence: high — Test: test_event_worktree_reuse_not_clean_does_not_consume_attempt
9. [blocking] No record-shape drift for downstream readers: the trigger path writes 014-shaped records (`gate=passed/failed`, budget extras, watermark key with a terminal `run_id`) that `_last_seen_event_ids`, `attempt_count_for_event`, status and notification consumers read unchanged; the pinned dispatch/worker-result record stays green with `tests/test_github_event.py` and `tests/test_triggers.py` otherwise passing unmodified. — confidence: high — Test: test_github_event_worker_result_history_record
10. [non-blocking] Docs/examples alignment: `deploy/jobs.example.yaml` shows the sugar form, `ROADMAP.md`'s G-98 area and 014/075 references describe one mechanism, and the stale "cannot be combined" validation text is gone; `validate`'s tick-timeout budget still holds for sugar-loaded jobs on every-tick cadence (pinned by `test_auto_fix_gate_systemd_timeout_budget` staying green) and the shipped history example and timeout docs stay truthful (`test_github_event_history_example_and_timeout_docs` staying green). — confidence: medium — Test: test_github_event_history_example_and_timeout_docs
